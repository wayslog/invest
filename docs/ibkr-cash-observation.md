## 60 日窗口与失败处理

初始化先完成真实 IBKR 只读预采集，然后按主机实际时钟选择尚未开盘的首个 XNYS 会话，
冻结连续 60 个交易日。预采集不计入观察天数，具体起止日保存于新登记中。

- 每个会话收盘 **60 分钟后**才可执行该日采集；下一 XNYS 会话开盘为及时观察截止。
  半日市、节假日及夏令时采用交易所日历。
- 在有效窗口内成功采集、核对并持久化，才累计一个及时观察日；重复任务不重复计数。
- 网络或 Gateway 失败留下真实失败记录并告警，下次任务可以重试。失败不生成成功日结。
- 错过截止时间的会话永久记为 `missed`，未来批次和恢复不能把它改成及时观察，窗口不延长。
- `sessions` 表示及时成功的天数；`missed_sessions` 表示永久漏跑数；`missing_sessions`
  表示当前已到采集时间但尚未处理的会话，历史漏跑不会让后续每次正常运行都失败。
- 观察窗口结束时单独报告覆盖情况。如果存在漏跑，就保留不足 60 次及时观察的结果。

后台沿用每小时日结 timer、十五分钟健康检查和 GitHub 独立监控。即使当前没有到期会话，
服务也核对账户、检查版本、创建对应本机备份并记录心跳。
报告同时显示来源、新窗口、及时观察进度和漏跑数，不能把部署检查次数当作观察天数。

## 部署与查询

本次重开通过 [Actions 部署](github-actions-deployment.md) 的固定 `operation=restart` 执行：

```bash
gh workflow run deploy.yml --ref main -f operation=restart
```

它使用固定请求 `m3-ibkr-cash-v1`，重试续接同一账户而不会再度清零。旧账户和 operations
归档到 `/var/lib/invest/archives/m3-ibkr-cash-v1/`，新账户使用 `/var/lib/invest/account`，
新运行记录使用 `/var/lib/invest/operations`，服务配置明确选择 `backend="ibkr_cash"`。
本次部署的请求和进度位于 `/var/lib/invest/restarts/m3-ibkr-cash-v1/`。
该目录也保存登记时的预采集证据，需要持续保留。新账户的本机备份保存登记、配置及事件；
所引用的行情批次仍保存在原始采集目录，备份不是独立的市场数据包。SDK 调用失败的
输出也保存为私有 Parquet 回执，便于排查 Gateway 或权限问题。

只有新的服务心跳、核对、备份、Telegram 和健康检查实际通过后，才启用 timer。
切换后失败保留新旧状态并停用 timer，之后续跑同一次请求，不回滚旧账户或重复初始化。

从 Actions 运行 `operation=inspect` 可查看不含私人账户数据的状态。主机上也可运行：

```bash
/opt/invest/current/.venv/bin/invest forward-status --account /var/lib/invest/account
/opt/invest/current/.venv/bin/invest forward-verify --account /var/lib/invest/account
```

`forward-backup` 和 `forward-job` 会识别新观察格式。通常由 systemd 作为唯一写入端执行，
不要同时人工运行另一个 writer。新观察不接受人为时间 `--at`、旧发行方证据或旧
`forward-control/migrate/run` 流程。版本变化仍须保留冻结记录，不能靠再次 `restart` 自动重置。

私人账户、原始数据、日志和本机备份留在 VPS；公开 Actions 只展示运行摘要。
